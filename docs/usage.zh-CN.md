# 作业工作流使用指南

这套 skill 让你在 AI 协助下自己写代码：AI 负责设计、答疑和批改，代码由你写，过程类似学校布置作业。目标不是让 AI 替你写得更快，而是让你在使用 AI 的同时，真正掌握自己仓库里的代码。

安装方法见仓库根目录的 [README](../README.zh-CN.md)。

## 一、整体流程

```
  需求小 ------------------------------+
                                       v
  需求大 --> [hw-plan] --> plan.md --> [hw-assign] --> assignment.md
             规划项目                   布置作业
                                           |
                     +---------------------+---------------------+
                     v                     v                     v
                 [hw-hint]           [hw-progress]          （自己写代码）
                 卡住求助              中期检查
                     |                     |
                     +----------+----------+
                                v
                           [hw-review] --- 需修改 ---> 回去改，再交
                            批改作业
                                | 通过
                                v
                          [hw-archive] --> 项目内作业：合并回 plan.md，
                           归档作业          解锁下一个作业
```

一个作业的状态只有四种：

```
  in-progress --(批改)--> passed --(归档)--> archived
       ^          |
       |          v
   changes-requested
```

## 二、怎么调用 skill

- **点名调用（最可靠）**：在消息里写出 skill 名，比如"用 hw-assign 布置作业……"，或者输入 `/hw-assign`。
- **自然语言触发**：除 hw-archive 外，其他 5 个 skill 都能从"布置作业""卡住了""交作业"这类说法自动触发。如果没有触发，就改为点名。
- **hw-archive 只能点名调用**。它会移动文件，所以不会被自动触发。

各 skill 都会用你所用的语言回复。

## 三、各 skill 的使用场景与提示词

### hw-plan：规划项目

**什么时候用**

- 需求比较大，包含多个可以独立交付的功能，需要拆成几个作业按顺序完成。
- 不确定要不要拆，想先和 AI 一起理清楚。
- 项目做到一半，需求变了，或者 hw-archive 报告某个作业的结果与后续计划冲突。

**它会怎么做**

像讨论一样推进：一次只问一个问题，用图展示拆分和依赖，按你对各项技术的熟悉度为每个作业建议档位。你明确确认之前，它不会写任何文件。结论只有两种：写入项目大纲 `plan.md`，或者告诉你"一个作业就够了"，然后交给 hw-assign。

**提示词**

开始规划：

> 用 hw-plan 规划一下：我想给项目加存档系统，包括本地存档、云同步和存档选择界面。

> 这个需求有点大，帮我拆成几个作业。

> （hw-plan）我想做一个命令行工具，支持 get/set/remove，数据存到 JSON 文件。先帮我想想要不要拆。

讨论过程中：

> 我对 System.Text.Json 不熟，相关作业给骨架档；文件读写我很熟，给架构档就行。

> 把 UI 相关的作业往后排，先把数据层做扎实。

> T2 太大了，再拆细一点。

> 先别写文件，我再想想。

确认写入：

> 可以，就按这个拆分写入。

重新规划：

> （hw-plan）调整项目 save-system：云同步先不做了，把它从计划里去掉。

> 归档时说 T3 和 T1 的接口有冲突，用 hw-plan 帮我调整一下。

**注意**

- 已归档的作业不能修改，要调整就新增一个作业。
- 进行中的作业受重新规划影响时，会被标记为"过期"。之后对它调用任何 skill，都会先和你核对、修正设计。

### hw-assign：布置作业

**什么时候用**

- 想自己实现某个功能，需要一份设计和验收标准。
- 项目大纲里有可以布置的下一个作业。

**它会怎么做**

先读你的代码，让设计沿用项目已有的结构和约定；有疑问时一次问一个。正式写入前，先给你看精简版（模块、验收标准 AC、进度清单 P），你确认后才写入 `assignment.md`，并记下基准提交。之后批改时，就以这个提交为起点判断哪些代码是你写的。无论哪个档位，它都不会写出可运行的实现。

**三个档位怎么选**

| 档位 | 给什么 | 适合 |
|---|---|---|
| 架构档 | 模块划分、职责、数据流、验收标准 | 熟悉的领域，接口也想自己定 |
| 规格档（默认） | 加上接口签名、数据结构、关键思路、边界情况 | 一般任务 |
| 骨架档 | 再加上写进代码文件的函数桩（只有签名和 TODO）、难点伪代码 | 陌生的领域或技术栈 |

**提示词**

布置独立作业：

> 用 hw-assign 布置一个作业：实现一个带过期时间的内存缓存，支持 Set、Get、Remove、Count。

> 布置作业：实现背包系统的物品堆叠和拆分。用骨架档，这块我不熟。

> 布置作业：给日志模块加按大小滚动。用架构档，接口我自己设计。

> 我想自己实现 JWT 校验中间件，帮我出个设计。

布置项目内的作业：

> （hw-assign）布置 T1。

> 布置项目 save-system 的下一个作业。

确认精简版时：

> AC-3 太严格了，去掉。

> 进度清单拆细一点，P-2 分成两步。

> 可以，写入吧。

处理提醒：

> 给这个作业绑定一个新分支 feature/inventory。（已有其他作业在同一分支上时）

> 骨架提交可以，创建吧。/ 不要提交，把函数桩写在文档里。（骨架档）

**注意**

- 布置前最好先提交或暂存手头的改动，否则它们会混进作业的改动范围。它会提醒你。
- 项目内作业要等它依赖的作业**归档**之后才能布置。只是批改通过还不够。
- 需求太大时，它会建议改用 hw-plan。你坚持的话，也可以按一个作业布置。

### hw-hint：分级提示

**什么时候用**

写代码时卡住了：不知道从哪下手、思路走不通、结果不对又找不到原因。

**它会怎么做**

提示分三级，你说不够才往上升：

| 级别 | 给什么 |
|---|---|
| 1 方向 | 问题在哪个位置或领域，该回看设计的哪部分 |
| 2 思路 | 解决步骤、可用的模式、要注意的陷阱，不给代码 |
| 3 片段 | 3 到 10 行关键代码，绝不给完整函数 |

每次提示都记在 `hints.md`。换一个新对话问同一个问题，会从上次的级别继续。

**提示词**

> 卡住了：Get 返回的值不对，过期的条目还能拿到。

> （hw-hint）存档反序列化总是丢字段，给点提示。

> 还是不太懂，再具体一点。

> 直接给第 3 级提示吧。

> 过期那个问题我还是没搞定。（新对话里继续之前的问题）

> H-2 那个问题我已经解决了。

> 还是写不出来，直接帮我写吧。（会先确认一次，然后记为"AI 代写"）

**注意**

- 提示会和作业设计保持一致。如果你的代码已经偏离设计，它会先指出偏离。
- AI 代写的部分会在批改和答辩时被重点关注。这不是惩罚，而是为了确认你理解了那部分代码。

---

### hw-progress：查看进度与中期检查

**什么时候用**

- 想看看手上有哪些作业、各自做到哪了。
- 写到一半，想确认方向对不对，免得写完才发现偏了。
- 隔了几天回来，想快速找回状态。

**它会怎么做**

对照代码推断每个进度项的状态，你确认后才更新进度清单。发现代码与设计不一致时，先问你是不是有意的：

- 有意的：记下你的理由，留到批改时评估，这里不评价对错。
- 无意的：问你要不要改法。需要的话，按 hw-hint 的分级规则给提示。

它不打分、不审查代码质量，也不改变作业状态。

**提示词**

> 我有哪些作业？

> 我做到哪了？

> 中期检查一下 memory-store。

> 写到一半了，帮我看看方向对不对。

回应它的推断和提醒时：

> P-3 其实还没写完，记成进行中。

> 这个偏离是有意的：Get 改成抛 NotFound，因为调用方需要区分"没有"和"值为空"。

> 不是有意的，给我个提示怎么改回来。

> 不是有意的，我自己改。

---

### hw-review：批改作业

**什么时候用**

作业写完了，或者按上次批改意见改完了。

**它会怎么做**

1. 只批改基准提交之后你改动的代码。
2. 逐条检查验收标准是否满足。
3. 评估与设计的偏离。设计是建议不是合同：理由合理的偏离会被认可，并写回设计；理由不合理的要改；没说明理由的，会先问你为什么这样实现。
4. 把代码问题分为"必须修改""建议""可选"三级。它只指出问题，不给修正代码，也不动你的文件。
5. 结论：验收标准全部满足、没有不认可的偏离、没有"必须修改"的问题时，结论为 `passed`；否则为 `changes-requested`。
6. 答辩（可选）：针对你卡过的地方、偏离的地方和 AI 代写的部分，提 2 到 3 个问题。答得不好只会列为"理解薄弱点"，不会因此打回。

**提示词**

> 交作业。

> 我写完了，批改一下。

> 批改并答辩。

> 交作业，这次不要答辩。

> 交作业。另外我把加载失败时抛异常改成了返回空存档，因为第一次启动时没有存档文件是正常情况。（主动说明偏离理由，省一轮来回）

> 改好了，再批一次。（返工后，会逐条复查上次的问题）

批改之后：

> R1-2 为什么算必须修改？

> 这个问题怎么改？（它会建议你用 hw-hint 获取提示）

**注意**

- 能用命令验证的（比如 `dotnet test`），它会运行验证。Unity 项目的测试需要在编辑器里跑，请把 Test Runner 的结果告诉它。
- 它不会临时增加新的验收要求。如果发现验收标准漏了重要内容，会作为"建议"提出，不影响结论。

---

### hw-archive：归档作业

**什么时候用**

作业批改通过（`passed`）之后。只能点名调用。

**它会怎么做**

- 把作业目录原样移到 `.homework/archive/日期-作业名/`。
- 项目内作业还会：把这个作业最终的接口和约定（包括被认可的偏离）合并进 `plan.md`，标记为已完成，并告诉你哪些作业现在可以布置了。
- 如果新确立的接口与后续作业的计划冲突，它会指出冲突，并建议用 hw-plan 调整，不会自己改计划。

**提示词**

> /hw-archive

> 用 hw-archive 归档 memory-store。

---

## 四、守护规则：新对话里的软提醒

第一次布置作业时，会在项目里生成 `.cursor/rules/homework-guard.mdc`。它在每个对话中都生效：

- 你请求实现的代码落在某个作业范围内时，AI 会先提醒"这属于作业 X 的范围"，建议用 hw-hint，并问你是否仍要直接实现。
- 你确认后照常实现，并把这部分记为"AI 代写"。
- 与作业无关的请求、提问和解释代码，都不受影响。

回应提醒的提示词：

> 那给我个提示吧。

> 确定，直接写。

## 五、典型场景

### 场景 1：一个小功能

```
你：用 hw-assign 布置作业：实现物品堆叠。用规格档。
     ……确认精简版，写入……
（自己写代码）
你：卡住了，拆分时数量算不对。               -> hw-hint 第 1 级
你：再具体一点。                            -> 第 2 级
（继续写）
你：交作业。                                -> changes-requested
（按意见修改）
你：改好了，批改并答辩。                     -> passed
你：/hw-archive
```

### 场景 2：一个需要多个作业的大功能

```
你：用 hw-plan 规划：存档系统，本地存档 + 云同步 + 存档界面。
     ……讨论、确认拆分，写入 plan.md（T1 本地存档，T2 云同步依赖 T1，T3 界面依赖 T1）……
你：布置 T1。
     ……完成、批改通过……
你：/hw-archive                            -> T1 的接口合并进 plan.md，提示 T2、T3 可以布置
你：布置 T2。                               -> 设计基于 T1 最终的接口
```

### 场景 3：隔了几天回来

```
你：我有哪些作业？                          -> 列出作业和一句话状态
你：中期检查一下 save-local。               -> 进度、记录在案的偏离
你：过期那个问题我还是没搞定。              -> hw-hint 从上次的级别继续
```

## 六、配置

`.homework/config.yaml`：

| 字段 | 默认值 | 作用 |
|---|---|---|
| `default_tier` | `spec` | 未指定档位时使用的档位：`architecture`、`spec`、`skeleton` |
| `language` | 空 | 作业文档正文的语言，如 `zh-CN`、`en`；留空则跟随你的语言。对话始终用你的语言 |
| `review.defense` | `false` | 批改时是否默认答辩；单次可以用"批改并答辩"或"不要答辩"覆盖 |

## 七、项目里会产生的文件

```
<项目>/
  .homework/
    config.yaml
    projects/<项目>/plan.md              项目大纲
    tasks/<作业>/
      meta.yaml                          状态、档位、基准提交
      assignment.md                      需求、设计、验收标准、进度清单、决策、偏离
      hints.md                           提示记录
      progress.md                        进度快照
      reviews/review-N.md                批改报告
    archive/<日期>-<作业>/               已归档作业
  .cursor/rules/homework-guard.mdc       守护规则
```

这些文件都写在 `.git/info/exclude` 里，只在本地可见：不会出现在 `git status` 中，不会被提交，也不会修改项目的 `.gitignore`。骨架档在你同意后会创建一个提交 `hw(<作业名>): scaffold stubs`，这是唯一会进入提交历史的内容。

## 八、常见问题

**换一个新对话，AI 还记得作业吗？**
记得。所有信息都在作业文件里，每个 skill 开始时都会从文件和 git 恢复上下文，不依赖聊天记录。

**能同时做几个作业吗？**
可以，但同一分支上同时做多个作业，改动会混在一起，批改时分不清。布置第二个作业时，它会建议你绑定一个新分支。项目内有依赖关系的作业只能按顺序做。

**AI 给的设计我觉得不好怎么办？**
布置时直接提出修改。如果写的过程中才发现问题，就按你认为对的方式写，交作业时说明理由；合理的偏离会被认可并写回设计。

**rebase 或 squash 之后，批改会出错吗？**
不会。基准提交找不到时，会改用基准分支与当前 HEAD 的合并基点，并告诉你发生了回退。

**我就是想让 AI 直接写某一部分，可以吗？**
可以。确认一次后它就会写，只是会记为"AI 代写"，批改和答辩时会重点看这部分。

**不想用了，怎么清理？**
删除项目里的 `.homework/` 和 `.cursor/rules/homework-guard.mdc`，再从 `.git/info/exclude` 删掉对应的两行即可。卸载 skill 本身见 README。
